# 90-Day Oracle Planning Workshop — Learning Lab UI Walkthrough Script

**Target duration:** 30 minutes  
**Format:** Live screen recording of the Learning Lab  
**Purpose:** Show learners how to enter the workshop, navigate the dashboard, use the 90-day plan, complete lessons, validate work, review Oracle screenshots, download practice files, and resume progress  
**Delivery style:** Professional, conversational, and practical  

## Recording preparation

- Record at 1920 × 1080 with browser zoom at 90% or 100%.
- Hide bookmarks, notifications, personal browser profiles, tenant URLs, and unrelated tabs.
- Use a fresh browser profile if you want the dashboard to begin at zero progress.
- Keep the cursor movement deliberate. Pause briefly before clicking so the viewer can follow.
- Do not rush through long pages. Scroll in short movements and stop at each section being explained.
- Use Phase 01 to demonstrate lesson structure, activities, validation, homework, and the exit gate.
- Use Phase 06 and Phase 07 for Oracle screenshot walkthroughs. Their required images are available.
- Do not open screenshot-based lessons in Phases 08 onward during this recording. Several later Oracle captures are still being completed.
- When demonstrating a validation failure, use an intentionally incomplete activity and explain that the feedback identifies what must be corrected.
- Do not complete the final exit gate during the recording unless you are using a disposable recording profile.

## Section 2 — Understanding the landing page

**Time:** 1:00–3:00  
**Screen:** Landing page.

2. Point to the main workshop description and the Apex journey card.
3. Scroll to the four summary metrics.
4. Continue to the implementation-journey and monthly-capstone cards.

**Narration:**

This is the public starting page for the workshop. It gives you a quick picture of what the training is about before you enter the learner workspace.

At the top, you can see the program identity: Production and Sales Planning, delivered as a 90-day guided workshop. The main description is important because it sets the expectation correctly. This is not only an Oracle navigation course. It is a complete implementation experience built around a realistic business case, guided application work, practical assignments, implementation evidence, and a connected monthly planning cycle.

On the right, the Apex journey card summarizes the business flow. Sales, production, inventory, and finance are connected. A change in one area affects the others, and the target outcome is an approved plan that is operationally feasible and financially aligned.

As we scroll down, the summary confirms the scale of the program: 90 workshop days, 27 implementation phases, one operational capstone, and one consistent business case.

The first card is the Implementation Journey. This is the core route for consultants, developers, solution architects, and learners who want to understand how the solution is discovered, designed, built, tested, deployed, and supported.

The second card is the Monthly Planning Capstone. It is not a separate parallel course. It is a seven-lesson final exercise in which implementation learners, planners, and business users operate the completed solution through one controlled monthly cycle.

For this walkthrough, we will enter through the Implementation Journey because that is where every new learner should begin.

## Section 6 — Reading the dashboard summary

**Time:** 7:00–9:15  
**Screen:** Dashboard hero, progress ring, statistics, and active module.  

**Presenter actions:**

1. Point to the journey heading and description.
2. Point to the progress ring and current-phase information.
3. Move across the four summary cards.
4. Point to the active-module card and lesson list.
5. Do not open the module yet.

**Narration:**

The dashboard is designed to answer three questions quickly: Where am I? What should I do next? And how does this work fit into the full program?

The large heading confirms the selected journey. On the right, the progress ring shows completion within your current phase. Beside it, you can see the phase number, phase title, and how many lessons have been completed.

The dashboard uses your most recent learning state to decide what to display as the active module. If you return later using the same browser profile, the **Continue** action takes you back to your current phase.

One practical note: in the current version, progress is stored in the browser. Use the same browser and device while completing the workshop unless your hosted training administrator confirms that account-based progress synchronization has been enabled.

## Section 7 — Using the 90-day program plan

**Time:** 9:15–12:15  
**Screen:** 90-day workshop plan.  

**Presenter actions:**

1. Click the **Combined 90-day workshop calendar** card or the sidebar plan link.
2. Show the hero summary with 90 days, 27 phases, 7 capstone lessons, and 9 submissions.
3. Scroll through the learning rhythm.
4. Show monthly-cycle coverage.
5. Show one calendar stage and one assignment card.
6. Show the milestone and Day 90 sections.

**Narration:**

The 90-day program plan is the main scheduling and orientation page. I recommend reviewing it before you begin and returning to it at the start of each new stage.

The top summary shows the complete scope: 90 program days, 27 implementation phases, seven capstone lessons, and nine assessed submissions.

The learning rhythm is repeated throughout the program: learn, apply, validate, capture evidence, and reflect. This is more than a design theme. It is the expected way of working. A lesson is not complete simply because you have read the explanation. You should be able to apply the concept, verify the result, and retain something that another person can review.

The monthly-cycle section shows where operational practice fits within the 90-day implementation. The seven capstone outcomes are not extra modules added after the workshop. Each outcome is rehearsed inside the relevant implementation phase and then executed as one connected Day 90 operating cycle.

The seven outcomes are actuals and data readiness, the demand baseline, sales forecast and consensus, inventory and supply feasibility, cost and financial impact, scenario review and approval, and finally publish, reconcile, and close.

The program calendar then organizes the work into Discover, Design, Build, Validate, Deploy, and Operate. Each period identifies the learning focus, the related phase or phases, the assignment, and the evidence expected.

Further down, the assignment section explains the nine assessed submissions. Each card tells you what to submit and what must be true for the work to be accepted. This is important because submission and acceptance are not the same thing.

The milestone section provides the checks used at the end of each stage. If figures do not reconcile, required evidence is missing, or an important decision has no owner, record and resolve the gap before treating the stage as complete.

At Day 90, the implementation evidence, the monthly planning capstone, and the business-as-usual handover come together in one final review.

## Section 8 — Finding phases and lessons

**Time:** 12:15–14:15  
**Screen:** Dashboard lifecycle, phase directory, and lesson directory.  

**Presenter actions:**

1. Return to the dashboard using the sidebar.
2. Scroll to the implementation lifecycle.
3. Point to the six stage cards.
4. Show the complete phase directory.
5. Show the lesson directory and expand the viewer's understanding without opening several pages.

**Narration:**

Back on the dashboard, the lifecycle view groups all 27 phases into the six project stages.

The stage cards help you understand the overall sequence. Discovery establishes the business need and current state. Design converts those needs into an approved future process and solution blueprint. Build creates the application and connected planning capabilities. Validate tests the complete solution. Deploy moves it into controlled use. Operate covers hypercare, support ownership, and continuous improvement.

The phase directory provides direct access to each phase. In a review or facilitator build, later phases may be available for reference. That does not remove the learning dependencies. For example, metadata should still be based on an approved application design, and application design should still be based on agreed requirements and architecture.

The lesson directory is useful when revisiting a specific topic. It lists the lessons inside each phase, their numbers, and estimated durations.

For normal learning, use the dashboard's active-module and next-lesson guidance. Use the directory when you need to review a completed topic, prepare for a workshop, or locate a specific procedure.

## Section 9 — Anatomy of a learning module

**Time:** 14:15–16:45  
**Screen:** Phase 01 — Discovery & Requirement Gathering, Lesson 01.  

**Presenter actions:**

1. Open **Phase 01 — Discovery & Requirement Gathering**.
2. Pause at the module header.
3. Point to the breadcrumb, phase number, title, description, and progress bar.
4. Point to the lesson navigation on the left.
5. Point to the exit gate at the bottom of the lesson navigation.
6. Point to the lesson status and footer controls.

**Narration:**

Every phase uses the same basic workspace, even though the lesson activities change.

At the top, the breadcrumb shows your current location and provides a direct link back to the dashboard. The module header shows the phase number, stage, title, objective, and completion percentage.

The left-hand panel contains the module contents. Phase 01 has seven guided lessons, beginning with Discovery foundations and ending with the Discovery pack and exit gate. Each lesson shows its sequence and estimated duration.

The exit-gate summary at the bottom tells you what the phase must produce before it is considered complete. For Phase 01, the objective is not merely to answer several questions. The phase must produce applied homework and an approved discovery pack that can support the Current-State Assessment.

In the main workspace, the lesson header shows the active lesson and whether it is in progress or completed.

At the bottom of the page, **Previous** and **Next** move between lessons. **Validate and complete** checks the current lesson. It does not simply mark the page as read. For interactive lessons, it checks whether the required decisions, fields, or answers have been completed correctly.

The left-hand lesson list is also clickable, so you can move directly to another lesson. However, completing lessons in order will give you the clearest experience because later activities build on earlier decisions.

## Section 10 — Completing and validating a lesson

**Time:** 16:45–19:15  
**Screen:** Phase 01, Lesson 01 followed by Lesson 02.  

**Presenter actions:**

1. Briefly scroll through Lesson 01.
2. Click **Validate and complete**.
3. Show the success message, completed status, updated progress, and completed icon.
4. Click **Next** to open Lesson 02.
5. Without entering answers, click **Validate and complete** once.
6. Show the targeted error feedback.
7. Do not fully complete Lesson 02 during the walkthrough.

**Narration:**

Lesson 01 is an orientation lesson. It explains why discovery exists, the sequence from business context to sign-off, and the difference between evidence-led discovery and premature configuration.

When I select **Validate and complete**, the lesson is marked complete because this orientation does not require a separate input activity.

Notice what changes. A confirmation message appears, the lesson status changes to Completed, the indicator in the left navigation is updated, and the module progress increases.

Now I will move to Lesson 02, Business context and scope.

This lesson contains actual decisions and written input. The learner must confirm the integrated business objective, identify the complete scope, choose an appropriate success-measure approach, and document a meaningful constraint or assumption.

If I try to validate the lesson without doing that work, the system does not accept it. Instead, it gives a targeted message explaining what is missing.

This feedback is there to guide correction. Read it carefully, return to the activity, and fix the incomplete or incorrect parts. A failed validation does not reduce a score or lock the lesson. It tells you that the evidence is not yet strong enough to mark the lesson complete.

Once the required inputs are correct, validate again. Retain any business artifact requested by the lesson; the green confirmation in the interface is progress feedback, not a substitute for your working file or evidence pack.

## Section 11 — Working with interactive activities

**Time:** 19:15–21:15  
**Screen:** Phase 01 lessons 02 through 05, shown selectively.  

**Presenter actions:**

1. Scroll through part of Lesson 02 to show choices, checkboxes, and a text field.
2. Click Lesson 03 and show the stakeholder selection and workshop approach.
3. Click Lesson 04 and show question classification, evidence selection, and the discovery note.
4. Click Lesson 05 and show the requirement builder and generated statement.
5. Do not fill every control.

**Narration:**

The interaction changes according to the skill being practised.

Some activities use radio buttons when one decision must be selected. Others use checkboxes when the correct result requires a complete set. Dropdowns are used for classification and mapping exercises. Text areas are used when the learner must explain a decision, record an assumption, or prepare a professional handoff.

In the stakeholder lesson, for example, you build a cross-functional participant map and choose an appropriate workshop approach. The objective is to avoid relying on one stakeholder to represent the entire organization.

In Questions and Evidence, you classify discovery questions, select the evidence needed to validate stakeholder claims, and write a note that separates known facts from assumptions and open questions.

The Requirements-to-Design lesson shows a different pattern. You map requirements to the Oracle design areas they influence, then use a structured builder to create an owned and testable requirement. As the fields are completed, the interface generates a readable requirement statement.

These activities are intentionally practical. Do not choose an answer only because it appears to be the most detailed. Ask which option protects the business decision, control, ownership, grain, or acceptance criterion described in the case.

## Section 12 — Homework, knowledge checks, and exit gates

**Time:** 21:15–23:30  
**Screen:** Phase 01 Lessons 06 and 07.  

**Presenter actions:**

1. Open **Applied discovery homework**.
2. Show the five mission tabs and their status indicators.
3. Open one written mission and one decision-based mission.
4. Open **Discovery pack and exit gate**.
5. Show the deliverable checklist, summary field, knowledge questions, and final approval button.
6. Do not submit the exit gate.

**Narration:**

Near the end of a phase, individual lesson concepts are brought together through applied homework.

Phase 01 contains five missions: drafting the discovery charter, assigning workshop ownership, preparing an evidence-validation plan, rewriting a vague request, and preparing the client readout.

The mission tabs allow you to work in manageable sections. A status indicator shows whether each mission has met its completion condition. Written missions require a meaningful response rather than a few words. Decision-based missions require the full set of correct mappings.

The final lesson is the phase exit gate. Here, you confirm that the required deliverables exist, summarize the approved discovery baseline, and complete the knowledge check.

The final action is labelled **Approve discovery pack** because it represents a phase-level decision, not just another page completion.

Do not select deliverables that you have not actually created. The checklist is there to confirm the evidence package, not to generate it. Store your working and final files in the folder structure defined by your facilitator.

If the exit validation fails, review the message and check three things: Is every required artifact present? Is the handoff summary complete and useful to the next phase? And are all knowledge-check answers correct?

Only after those conditions are met should the phase be treated as ready for handoff.

## Section 13 — Using Oracle screenshot walkthroughs

**Time:** 23:30–26:30  
**Screen:** Phase 06 — Application & Dimension Design, Lessons 02, 04, and 05.  

**Presenter actions:**

1. Use the dashboard or phase directory to open Phase 06.
2. Acknowledge the earlier-phase recommendation if it appears in the recording profile.
3. Open Lesson 02, **Application setup walkthrough**.
4. Scroll through two or three captured steps.
5. Open one screenshot at full size in a new tab, then return.
6. Point to **What this screen shows**, **Navigation**, **Trainee action**, and **Validation evidence**.
7. Briefly show Lesson 04 and Lesson 05 to demonstrate hierarchy, currency, cube, and valid-intersection captures.

**Narration:**

Now let us look at the Oracle screenshot walkthrough format using Phase 06, Application and Dimension Design.

If an earlier-phase recommendation appears, read it before continuing. The workshop may allow you to review a later phase, but the prerequisite still explains which approved evidence should exist before you perform the task in a real training tenant.

Lesson 02 contains the controlled application setup walkthrough. Each step includes a real Oracle capture from the authorized training environment.

The screenshot is only one part of the instruction. Under each image, the lesson explains what the screen shows, where to navigate, what the trainee must do, and what evidence proves that the action was completed correctly.

You can select an image to open it at full size. Use this when you need to inspect Oracle labels, selected values, or surrounding navigation. Then return to the lesson and read the action and evidence together.

For example, the application-details step is not asking you simply to copy values from a picture. It asks you to compare the calendar, workflow, multicurrency choice, cube names, and optional features with the approved design. The correct value comes from the case design; the screenshot helps you locate and verify it in Oracle.

The later screenshot lessons use the same pattern. The hierarchy and member-properties walkthrough shows how to review structures and high-impact properties. The cubes and intersections lesson shows the Plan1 BSO input-and-calculation cube, the ApexPlan ASO reporting cube, the governed data movement between them, and the valid-intersection controls used to prevent meaningless combinations.

When a walkthrough provides an Oracle reference link, treat it as supporting documentation. The workshop case and approved design still determine what you should configure.

Never use a client or production tenant for these exercises. Work only in the authorized training environment and make sure any evidence you retain is sanitized.

## Section 14 — Downloading practice files and using build evidence

**Time:** 26:30–28:15  
**Screen:** Phase 07 — Metadata Build, Lessons 02 through 04.  

**Presenter actions:**

1. Open Phase 07 from the phase directory.
2. Open Lesson 02, **Prepare and validate metadata files**.
3. Point to the complete practice-pack download and several individual files.
4. Explain the staging-file warning.
5. Open Lesson 03 or 04 and show a completed Oracle screenshot walkthrough.
6. Do not download every file during the recording.

**Narration:**

Phase 07 demonstrates how hands-on files are provided.

In the file-preparation lesson, you can download the complete practice pack or individual items such as the clean Product file, the defective Product exercise, Entity and currency assignments, Account design policy, expected counts, and the metadata build checklist.

Read the instruction above the downloads carefully. These files are training source and staging exercises. They are not guaranteed to be direct Oracle import files for every environment. The controlled process is to export the target dimension from the authorized training tenant, preserve the supported headers and property values, and map the prepared rows into a reviewed copy.

This distinction matters. A realistic implementation does not assume that a spreadsheet is safe to load because it has familiar column names.

The manual-build and bulk-import lessons then use complete Oracle captures to show the dimension editor, metadata export, import file selection, import options, and job-status review.

As in Phase 06, every captured step includes the navigation path, trainee action, and validation evidence. The evidence may include a job identifier, accepted and rejected row counts, reviewer confirmation, refresh result, or an expected-versus-actual reconciliation.

When a practice pack includes both clean and defective data, the defective file is intentional. It is there so you can practise detecting, classifying, correcting, and safely rerunning a failed build rather than only seeing the successful path.

**Narration:**

When you return to the dashboard, the progress summary reflects the lessons completed in this browser.

Use **Continue module** or **Current module** to return to your active work. The system also remembers the lesson you last opened, which makes it easier to resume after a break.

Progress tracking is useful, but maintain your own evidence discipline as well. Keep downloaded files, working versions, final artifacts, validation results, review comments, and approvals in an organized workshop folder.

Do not mark a lesson complete merely to increase the percentage. The value of the program comes from being able to explain the decision and show the evidence behind it.

If you are using a shared computer, a private browsing session, or a browser that clears local storage, confirm the progress arrangement with your facilitator before relying on the dashboard alone.
